## 1. Understanding of Concepts

After reading the document, the main thing I understood is that we shouldn’t classify web communication technologies just by popular names or tools. Instead, we should think about what problem each technology is trying to solve. The document breaks this down into a few areas that work together: the communication pattern, the API or interaction model, how data is represented, the application or messaging protocol, the transport layer (including sockets and addressing), and some cross-cutting concerns like security and reliability. These are not strict layers that you must follow in a fixed order every time. In real projects, things like browser support, latency, security rules, and available infrastructure can affect earlier choices too. It also points out that one technology can cover more than one of these areas. For example, gRPC is not just one thing because it involves an RPC framework, usually Protocol Buffers for serialization, and HTTP/2 for transport. QUIC also mixes transport behavior with security features based on the TLS 1.3 handshake.

When it comes to communication patterns, the document explains different ways systems exchange information. Request–response is the most familiar one, where a client sends a request and expects a result, status, or error back. This can be synchronous or asynchronous in code, but the pattern is still the same. HTTP APIs, unary gRPC, SOAP operations, and JSON-RPC fit here, and it makes sense when the caller actually needs the answer before moving on.

Then there are message queues, which are usually used for background work. A producer puts a task on a queue and a consumer processes it later, often with multiple workers competing so that each message is handled by one of them. What I found important here is that things like acknowledgements, retries, dead-letter handling, persistence, and redelivery depend on the broker and its settings. A queue does not automatically mean exactly-once processing, and it also doesn’t mean messages can never be kept or replayed.

Publish–subscribe or a message bus is a bit different because one published message or event can go to multiple subscriber destinations. Each service can react on its own, like when a `StudentRegistered` event is needed by attendance, billing, and notification services. The document makes a good point that publish–subscribe is the interaction pattern, while a message bus is more of an architectural idea for shared routing and distribution, not a specific wire protocol.

Event streams or append-only logs take this further by keeping events in a retained, ordered log (often split into partitions). Consumers keep track of their own offsets, so they can read independently and sometimes replay old events if they are still retained. In Kafka, for example, consumers in the same consumer group share partitions, but different groups can read the same topic separately. Ordering is usually guaranteed within a partition or a defined scope, not across everything. This is why an event stream is not just “a queue with many readers.”

The document also talks about streaming in different directions: client-to-server streaming, server-to-client streaming, and bidirectional streaming. SSE is mentioned as a browser-facing way for the server to push updates to the client over HTTP using `EventSource` and `text/event-stream`, and it’s not a transport protocol. For notifications, long polling keeps a client request open until there is data or a timeout and then the client sends another request, while webhooks are server-to-server HTTP callbacks to a registered endpoint. With webhooks, the receiving system has to be reachable and should validate the sender, handle duplicates, and respond properly to retries.

For API and interaction models, I learned to separate the style or model from the protocol. REST is an architectural style based on resources and representations and is commonly used with HTTP, but REST and HTTP are not the same thing. GraphQL is a query language and execution model where the client asks for specific fields using a typed schema. gRPC is an RPC framework where clients call methods from service contracts, commonly using Protocol Buffers and HTTP/2. SOAP is a structured messaging framework, often XML-based, while JSON-RPC and XML-RPC are RPC protocols that encode calls in JSON or XML. WebSocket, on the other hand, is not an API style; it’s a protocol for persistent bidirectional communication, and the application still has to define its own message format.

Data representation is another separate concern. The same object can be encoded in different ways, like JSON, XML, or binary formats such as Protobuf or Avro, and there are also formats like MessagePack, CBOR, CSV, and media/document formats such as images, video, or PDF. Serialization turns application objects into bytes and deserialization turns them back. The document also explains that `Content-Type` and `Accept` in HTTP help with interpreting representations, and compression (like gzip or Brotli) is different from serialization.

On the protocol and transport side, HTTP/1.1, HTTP/2, and HTTP/3 all carry HTTP semantics but work differently underneath. HTTP/2 uses multiplexed streams over one TCP connection, but if there is packet loss, TCP’s ordered byte stream can still delay other streams on that same connection. HTTP/3 runs over QUIC on top of UDP, which supports independent streams, connection migration, and built-in security using the TLS 1.3 handshake. WebSocket starts with an HTTP upgrade in the classic HTTP/1.1 case (101 Switching Protocols) and can also be bootstrapped over HTTP/2 and HTTP/3 using Extended CONNECT. For messaging, MQTT and AMQP are messaging protocols (and AMQP has different versions like 1.0 and 0-9-1), while Kafka is better described as an event-streaming platform with its own client-broker protocol, partitions, offsets, and consumer groups.

Transport and addressing were also explained clearly. TCP gives a reliable, ordered byte stream but does not keep message boundaries, so applications need framing (like length prefixes or delimiters). UDP keeps datagram boundaries but does not guarantee delivery, ordering, or retransmission. QUIC runs over UDP but provides its own transport features like reliable streams and flow control. An IP address identifies a network endpoint or host, while a port identifies the service/application endpoint on that host. A socket is usually described using protocol, IP, and port, and a TCP connection is identified by both source and destination IPs and ports. A device does not always need a public IP directly because private addresses, NAT, reverse proxies, or load balancers are commonly used.

Finally, the cross-cutting concerns tie everything together. Security includes transport protection like TLS/HTTPS/QUIC security and message-level protection like JWS/JWE, and it also separates authentication, authorization, and identity (for example OAuth 2.0 vs OpenID Connect, and JWT as a claims format that may be signed or encrypted). Reliability includes timeouts, bounded retries with backoff and jitter, idempotency, delivery semantics (at-most-once, at-least-once, and scoped exactly-once guarantees), circuit breakers, bulkheads, backpressure, acknowledgements, and dead-letter handling. Infrastructure components like API gateways, load balancers, reverse proxies, and service meshes can be arranged in different ways depending on the system. Observability involves logs, metrics, and traces, along with correlation/trace context (like W3C `traceparent`) and health checks.

### Concepts I think are most important

The most important idea for me is to classify technologies by the problem they solve and keep these dimensions separate. This helps avoid common mistakes, like thinking REST and HTTP are the same thing, or treating a data format as if it decides the transport. It also makes design choices easier to explain.

Another important point is that delivery behavior and topology are design choices, not just features of a product name. Knowing the difference between competing consumers in a queue, fan-out in pub/sub, and replayable event streams matters a lot in distributed systems, especially when duplicates or retries can happen.

I also think the document does a good job showing that guarantees depend on boundaries and layers. TCP gives a byte stream but no message boundaries, transport security is different from message security, and HTTP/2 over TCP can still be affected by packet loss in ways that HTTP/3 over QUIC handles differently because of independent streams.

Lastly, cross-cutting concerns are not optional extras. Things like idempotency, retry limits, trace propagation, and clear authentication/authorization boundaries are what make a system easier to run, debug, and keep reliable when something fails.

## 2. Technical Understanding

The way I see it, the document suggests a practical way to think through a design: start with the communication pattern, then decide how the interaction is expressed, choose a data representation, pick the application or messaging protocol, use an appropriate transport and addressing setup, and apply cross-cutting concerns throughout. Even though this looks like a sequence, it doesn’t always happen in that exact order. Sometimes a constraint forces you to rethink an earlier choice. For example, if you need browser-based server push you might lean toward SSE or WebSocket, if you need a typed service-to-service RPC setup gRPC may fit, and if you are in an IoT setting MQTT might be more suitable.

These dimensions are connected in a flexible way. A request–response pattern fits naturally with HTTP APIs, unary RPC, or SOAP operations. One-way live updates to a browser often fit SSE or HTTP streaming, while ongoing two-way communication fits WebSocket or bidirectional gRPC streaming (and WebRTC in peer media/data cases). Pub/sub, queues, and streams usually depend on brokers or platforms and their protocols, not just plain HTTP request–response.

The interaction model and data representation also go together. REST is centered around resources and representations, and HTTP headers like `Content-Type` and `Accept` help describe and negotiate them. GraphQL defines a typed query and response shape, often sent as JSON. gRPC uses service contracts with an IDL and commonly serializes messages with Protocol Buffers. SOAP and the RPC protocols like JSON-RPC/XML-RPC define their own message structures and encodings.

At the protocol and transport level, HTTP/1.1 and HTTP/2 run over TCP, while HTTP/3 runs over QUIC over UDP. Classic WebSocket connections upgrade from HTTP/1.1 over TCP, but there are also ways to bootstrap WebSocket over HTTP/2 and HTTP/3. Because TCP is a byte stream, applications must handle message framing themselves when needed. UDP keeps datagram boundaries but pushes concerns like reliability and ordering to the application if they are required. IP gets packets to the right endpoint, ports direct traffic to the right service on that endpoint, and things like NAT, proxies, and load balancers affect how services are exposed.

Cross-cutting concerns apply across all of this. TLS or QUIC security protects data in transit on a path, while JWS or JWE can protect a message or token itself. Retries, timeouts, and idempotency matter in both request–response systems and at-least-once messaging. Observability also has to carry across service boundaries, for example by passing trace context so logs, metrics, and traces can be connected.

There are also several distinctions in the document that I think are really important to keep straight. REST is an architectural style, not the same thing as HTTP, and HTTP/2 is not an “alternative to REST” because it changes how HTTP runs underneath. SSE is not a transport protocol, and WebSocket is not an API style. A work queue, a pub/sub fan-out setup, and an event log/stream solve different problems even if a broker can support more than one model. MQTT and AMQP are messaging protocols, while Kafka is a platform built around retained partitions, offsets, and consumer groups. Serialization, compression, and transport are separate things. TCP, UDP, and QUIC provide different guarantees, and HTTP/3 should not be pictured as plain TLS layered over QUIC in the same way as HTTPS over TCP. Transport security is different from message security, and an IP address is not the same as a port or as public reachability.

The student registration example in the document helped connect these ideas. In that case, a `StudentRegistered` event is a good fit for publish–subscribe because attendance and notification services need to react independently. The event can be serialized with an agreed schema (like JSON, or Avro/Protobuf if schema governance matters), and the broker choice depends on needs like replay and operations (for example separate queues in RabbitMQ or separate consumer groups in Kafka). It also brings in cross-cutting concerns like TLS, acknowledgements, idempotent consumers, retries, dead-letter handling, and trace context.

## 3. Critical Analysis

In general, I think the document is very clear and careful. It explains common misconceptions well and usually mentions when behavior depends on the broker, configuration, or scope. Still, there are a few places where I think the explanation could be made even clearer for students.

One small issue is the way the design flow is shown. The document does say the order is for reasoning and not a strict implementation rule, but the step-by-step flow can still look like a fixed stack where each choice must come only after the previous one. In practice, the process is often more back-and-forth. For example, transport limits, browser support, or an existing Kafka/RabbitMQ setup might force you to change an earlier design choice. A short note on the diagram saying that constraints can feed back into earlier decisions would make this clearer.

Another point is the explanation of HTTP/2 and TCP head-of-line blocking. The document is correct that packet loss can delay data for multiple HTTP/2 streams sharing one TCP connection, but a reader might think all progress stops in every situation or forget that HTTP/2 still improves on opening many separate HTTP/1.1 connections. It might be a bit clearer to say that packet loss can delay delivery or processing for other streams on the same connection until recovery, while still noting that multiplexing is useful.

The part about WebSocket bootstrapping over HTTP/2 and HTTP/3 is accurate, but it is quite brief. Since support can vary across clients, servers, and intermediaries, someone implementing it might assume it works the same everywhere. Adding a note that Extended CONNECT support should be checked end to end in the actual deployment path would be helpful.

I also agree with the document’s warning about exactly-once semantics, but I think it could go one step further by mentioning “effectively-once” processing. The document correctly says exactly-once guarantees are usually limited to a defined boundary and that true end-to-end exactly-once across independent systems and external side effects is hard. In many real systems, teams aim for effectively-once results by combining at-least-once delivery with idempotent consumers or deduplication within a clear boundary, so naming that idea would make the point easier to apply.

The document describes DNS as an application-level protocol, which is common in the Internet protocol suite view, but some textbooks explain naming and resolution a bit differently. This is more of a wording issue than a technical mistake. A small parenthetical note saying that DNS operates at the application layer in the Internet protocol suite and provides a naming/resolution service for applications could prevent confusion.

Finally, the difference between broker capabilities and the intended delivery topology is explained well, especially with the RabbitMQ example where consuming from the same queue means workers compete for messages. Since misconfigured bindings, queues, or subscriptions are a common source of bugs, it might help to highlight that warning earlier when queues and pub/sub are first compared. That would remind readers to check that the setup actually matches the fan-out or work-sharing behavior they want.

Overall, I don’t think these are major errors. They are mostly small clarifications that would make the document even easier to understand. The main message of the document is solid: choose technologies based on the problem, keep the design dimensions separate, and be clear about guarantees, security, and operational concerns.
